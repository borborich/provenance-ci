Five dimensions

Keep different questions separate.

Provenance CI does not collapse credential presence, cryptographic validation, trust, continuity, and policy into one misleading “authentic” label.

01 / presence

Is a credential present?

Absence is recorded as evidence, not as proof that content is false or AI-generated.

02 / cryptography

Does validation succeed?

The official CAI C2PA SDK performs parsing and validation behind a narrow adapter.

03 / trust

Was trust checked?

Trust requires an explicitly supplied, pinned local PEM snapshot. Otherwise it is not checked.

04 / continuity

How does this checkpoint relate?

Exact bytes and validated declared parent lineage are distinct forms of continuity evidence.

05 / policy

What does your CI require?

Versioned policy maps evidence to pass, warning, deterministic failure, or inconclusive status.

scope / v0.1.1

Local JPEG validation

No signing keys, user accounts, hosted scanner, remote manifest retrieval, or asset telemetry.

Five-minute start

Add a checkpoint test to GitHub Actions.

The Action needs only read access to repository contents. Assets remain on the caller's runner; the optional uploaded artifact is the versioned JSON evidence result. 

permissions:
  contents: read

steps:
  - uses: actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd
  - uses: borborich/provenance-ci@v0.1.1
    with:
      config: provenance-ci.yml

What this tool does not prove Provenance CI does not determine whether an image is true, authentic, human-created, AI-generated, unmanipulated, correctly copyrighted, or signed by an entity that deserves trust. It reports evidence available at the supplied checkpoints and explicitly records limitations.
