Concepts

Present, valid, trusted, continuous, and allowed are different

A useful C2PA CI result must not collapse distinct observations into one “authentic” label. Provenance CI records five dimensions so a policy decision can be explained and reproduced.

Content Credentials Publishing pipelines Updated 2026-07-29

Short answer

A JPEG may contain a credential whose cryptographic binding validates while trust was never checked. A changed JPEG may still be a valid declared derivative of the previous checkpoint. A technically valid result may still fail a repository's policy. None of these states establishes that the depicted content is true.

The five dimensions

Dimension Question answered Question not answered
Presence Did the SDK find a Content Credential for these bytes? Is the content true or false?
Cryptographic validation Did the evaluated binding, signature, and referenced structures validate? Does the signer deserve trust?
Trust Did the signing chain validate against the explicitly supplied trust snapshot? Is every assertion factually correct?
Continuity Are adjacent checkpoints exact bytes or linked by validated declared parent evidence? Which hidden component caused an observed break?
Policy Does this evidence satisfy the repository's versioned CI requirements? Is the content authentic, original, or lawful?

Presence is not validation

A parseable manifest store can be present while its cryptographic binding fails. Conversely, no credential may be present at all. Provenance CI reports these states separately so “absent” is not mislabeled as “invalid” and “present” is not mislabeled as “valid.”

Absence is a narrow observation. It does not prove that an asset is manipulated, false, or AI-generated.

Valid is not trusted

Cryptographic validation evaluates the credential and asset binding. Trust additionally depends on a configured trust decision. Provenance CI never downloads trust anchors implicitly: the user must supply a pinned local PEM snapshot. 

trust:
  anchorsPath: ./C2PA-TRUST-LIST.pem
  id: https://github.com/c2pa-org/conformance-public/commit/<commit>

If no snapshot is supplied, the result says not_checked. This is deliberately different from untrusted.

Changed bytes do not automatically break continuity

Publishing transforms often change JPEG bytes. Byte inequality alone cannot decide C2PA continuity. Provenance CI can report a valid declared derivative only when the current valid manifest includes validated parent evidence that matches the prior active manifest.

Adjacent checkpoint examples

same bytes → exact continuity evidence

changed bytes + validated parent → declared derivative evidence

changed bytes + no verifiable parent → changed without verifiable lineage

Perceptual similarity is not substituted for declared C2PA lineage.

Continuity is not policy

Teams can require a credential, a valid binding, checked trust, or a specific continuity relationship. The versioned policy converts recorded evidence into a stable exit code without changing the underlying observations. 

policy:
  requireCredential: true
  requireValidBinding: true
  requireTrusted: false
  continuity: exact-or-declared-derivative
  onInconclusive: warn

Truth is outside all five dimensions

C2PA is provenance metadata, not a truth oracle. A valid and trusted Content Credential can provide tamper-evident provenance statements and bindings. It does not independently prove the factual truth of every assertion, authorship, copyright, originality, or absence of manipulation.

Read the C2PA Technical Specification for the standard and the official CAI Rust SDK used behind the project adapter.
